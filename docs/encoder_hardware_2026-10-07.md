# TIM8エンコーダーの実機デバッグ（2026-10-07）

移植前後の同条件評価は[通常DMA／循環DMA比較](encoder_ab_2026-10-07.md)を参照。
CPU側の占有時間は少し減ったが、現在の循環DMA構成ではFOC角度の鮮度が悪化した。

接続: COM6、921600 bps、STLINK-V3MINIE。電源24 V / 電源側電流制限3 A、当初は負荷あり。
電源側の3 Aとモーター相電流は異なる。ホスト試験では相電流peak 5 A、速度200 rpmを中止条件とした。

## 再現・修正した不具合

修正前にVq=+0.1 V、ADCログ200 Hz、FOC/angle statusの繰返しで `fault=main stale` を再現した。
約0.42秒で保護停止。エンコーダーのspi/parity/sensor/timeout/overrunsは全て0で、前回ユーザーが報告したPARERRとは別の問題。

`angle status`は浮動小数点整形を含む複数行を一度に出力し、FOCの20 ms main watchdogを妨げ得る構成だった。
`as5047p.c`だけで以下を修正した。CubeMX生成領域と保護閾値は変更していない。

- 機械角・未校正電気角の表示を整数のミリ度換算へ変更。
- 遅延時間の表示を整数換算へ変更。表示単位・小数桁数は維持。
- `angle status`はmainループ1回につき1行を出力。起動時だけ停止中に全行出力。

修正版Releaseを書込み・Verifyした。同じ+0.1 V/約3秒/200 Hz/詳細表示繰返しではmain staleを再現しなくなった。
ただし、この表示負荷試験ではADC `log_overrun` が61に増えた。これをログ欠落なしの合格とは扱わない。

## 遅延の割り込みトレース

ユーザーより治具の擦れの可能性が報告された。回転むらの原因として考えられるが、ここでは遅延を調査。
無負荷・Vq=+0.3 V、ADCログなし、約2秒で既存の`angle trace`を取得した。
FWやCubeMX設定は変更せず、ホスト試験スクリプトにTrace指定を追加。
ログ: `build/encoder_irq_trace_2026-10-07.log`。
エンコーダー・UARTエラー0、相電流peak 1.320 A、終了時PWM停止・COM6解放済み。

256イベントはFOC開始直後の約1.834 msをカバーする。完全なRX区間36個のうち28個で
優先度0のTIM1/ADCが優先度1のRX処理を中断していた。

| 区間（入口〜出口） | 最小 | 中央値 | 最大 |
|---|---:|---:|---:|
| TIM1 ISR | 3.806 µs | 3.806 µs | 3.831 µs |
| ADC ISR | 29.231 µs | 30.238 µs | 30.244 µs |
| RX ISR（中断時間を含む） | 8.181 µs | 43.181 µs | 43.350 µs |

RX最長区間の内訳（RX入口を0とした相対時刻）:

| 時刻 | イベント |
|---:|---|
| 0 µs | エンコーダーRX入口 |
| 0.456 µs | TIM1入口、RXを中断 |
| 4.288 µs | TIM1出口 |
| 4.713 µs | ADC入口 |
| 34.950 µs | ADC出口 |
| 42.750 µs | エンコーダー角度公開後の記録 |
| 43.350 µs | RX出口 |

この区間はTIM1+ADCが34.069 µsを占め、差引き9.281 µsはRX処理と割り込み遷移等。
遅延の主要因として高優先度ISRによる待ちを実測で確認できた。
`adc_control_max`はADC ISR全体ではなくコールバック内部からの計測なので、
既存ログの約25〜27 µsと今回のADC ISR約30 µsは計測区間が異なる。

限界: トレース自体に計測負荷があり、開始直後しか記録しない。
ADCログ開始はこの記録窓より後になるため、ADCログあり条件の最悪47.58 µsを
直接捕捉した結果ではない。また送信予定時刻から測るcommit_delay_maxとRX入口からの43.35 µsは別指標。
次の対策検討ではADC/TIM1 ISR内の処理量・実行タイミングを確認する。
優先度の変更は電流制御に影響するため先行して行わず、必要なCubeMX変更はユーザーに依頼する。
