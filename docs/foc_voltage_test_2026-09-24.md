## 修正した問題

初版は底側25.68 µsでPWM更新締切に間に合わず停止した。
電圧演算の比較・平方根を単精度化し、三角関数を同梱CMSIS-DSPのテーブル補間へ変更。
FOC/電圧演算/CMSIS三角関数の3ファイルはDebugでも-O2を適用する。
CubeMX設定やCORDIC設定は変更していない。

多数の浮動小数点を状態表示するとmain監視20 msを超える問題も再現した。
状態表示を整数mV/mA/mrad/nsへ変更し、表示を繰り返しても継続することを確認した。
締切監視・main監視の閾値は緩めていない。

## その後のPWM更新方式変更

## Debug停止原因の調査

Vd=0、Vq=0.05 V、文字間2 msで比較。保護閾値・CubeMX設定は変更していない。

| 構成 | 結果 | 最大転送時間 |
|---|---|---|
| 元のDebug（診断追加前のas5047p.cでも再確認） | encoder age limit、77周期で停止 | 94.13 µs |
| 最初の異常記録を追加したDebug | 7回すべてencoder age limit（37〜357周期） | 94.26 µs |
| 切り分け用にas5047p.cのみ-O2追加 | encoder age limit、301周期 | 71.26 µs |
| 上記にcurrent_sense.cの-O2も追加 | encoder age limit、41周期 | 68.48 µs |
| 診断追加版Release | 明示stopまで運転継続、busy_ticks=0 | 43.25 µs |

Debugでは有効角度の要求時刻からの古さが約250.6〜251.0 µsになり、250 µs制限で停止した。
SPI/パリティ/センサー/転送タイムアウトのカウンタはすべて0。診断値0x0171。
50 µs後の次回要求時にも転送中となるbusy_ticksが増加した。

コードではTIM1/ADCのIRQ優先度が0、SPI/DMAが1であり、DMA完了処理は高優先度ISRの終了を待つ。
転送時間にはこの待ち時間が含まれる。Debugで取得が周期をまたぐことは実測できた。
周期をまたぐ角度取得に、20 msごとの診断取得（その回は角度を更新しない）が重なると、
有効角度の更新間隔がさらに延びる。これはコードと実測値からの原因分析であり、
各ISR占有時間と診断フレームの時系列を別々に計測したものではない。

前回のencoder invalidは今回再現しなかった。これはGetSampleがfalseになったことを示し、
今回のencoder age limitとは判定経路が異なる。前回の直接原因を確定したとは扱わない。
今回確認したのは、Debugの取得処理に時間余裕がなく、角度鮮度で停止する再現性のある問題である。

効果不十分だった追加-O2設定は元に戻した。再発調査用としてas5047p.cに最初の異常を保存する
診断だけ残した。angle statusで理由、転送段階、経過ns、SPI SR、DMA残数/フラグを表示する。
ISR内ではprintfせず、復旧しても記録を保持する。記録はMCUリセットでクリアされる。
角度の250 µs制限自体はこの記録の対象ではなく、foc statusの停止理由と最大角度年齢で確認する。

次の修正では、高優先度ISRの占有時間を計測して削減し、角度取得が1周期内に完了する構成を検討する。
タイムアウト/鮮度制限を緩めるだけの変更は行わない。
Release/Debugビルド成功。実機は診断追加済みReleaseに戻し、Vq=0.05 Vで継続運転・stopを確認。
最終PWM停止、COM11解放済み。校正値のFlashは変更していない。


## ISR時系列による切り分け

DWTでTIM1/ADC/RX DMAの入口・出口、要求開始、各フレーム送信開始直前、角度公開を記録。
最初の256イベントをRAMに保存し、stop後に出力した。Vq=0.05 V、RCR=1。
計測フック自体の負荷を含む。ハードウェアのTC発生時刻や例外入退場命令は直接測っていない。

- [Debug生記録](irq_trace_debug_2026-09-24.txt)
- [Release生記録](irq_trace_release_2026-09-24.txt)

時刻は160 MHzのサイクル数（160で割るとµs）。イベント番号は1/2=TIM入口/出口、
3/4=ADC入口/出口、5/6=RX DMA入口/出口、7=TX開始直前、8=要求開始、9=角度公開。

Debugで元のencoder invalidを再現した。停止時の最初の異常は
TIM transfer timeout、state=3（応答処理）、100.743 µs、SPI SR=0x2、RX/TX残数=0、DMAフラグ=0。
送受信は完了し、DMA ISRも完了フラグをクリア済みだったが、応答処理がTIM1に
プリエンプトされた。そのTIM1内で100 µsを超えたと判定し、角度を無効化してFOCが停止した。
従って今回のencoder invalidは電気的な通信エラーではなく、CPU側で応答処理が完了しないまま
転送状態がRESPONSEに残ったことによるタイムアウトだった。

Debug最初の正常な角度公開までの例（時刻は最初のTIM入口基準）：

| イベント | 時刻µs |
|---|---:|
| 要求開始 | 2.538 |
| 第1フレーム送信開始直前 | 7.438 |
| TIM終了 | 27.325 |
| ADC開始→終了 | 27.806→43.663 |
| 第1 DMA処理開始 | 44.144 |
| TIMによる中断 | 49.894→71.431 |
| 第2フレーム送信開始直前 | 74.719 |
| 第1 DMA処理終了 | 75.563 |
| ADC開始→終了 | 76.300→92.256 |
| 第2 DMA処理開始 | 92.738 |
| TIMによる中断 | 100.050→121.638 |
| 角度公開 | 123.319 |

要求→公開120.781 µsのうちTIM/ADC区間との重なりは99.725 µs（約83%）。
第1 DMA ISRは経過31.419 µs、うちTIM中断21.538 µs、自身の処理9.881 µs。
第2 DMA ISRは経過31.263 µs、うちTIM中断21.588 µs、自身の処理9.675 µs。
最初の送信開始→DMA入口は36.706 µsで、線上の16 bit転送3.2 µsを大きく超える。
差にはIRQ遅延・DMA起動命令等が含まれ、TCから入口までを直接計測した値ではない。

Release最初の要求→公開は45.369 µs、TIM/ADC区間との重なり28.625 µs。
第1 DMA自身の処理7.038 µs、第2は6.700 µs。ADC ISRは約10.46 µs、
Debugでは約15.86〜15.96 µsだった。
Releaseでも計測中はbusy_ticks=6を記録したため、計測負荷を含めた全転送が1周期内に
収まるとは言えないが、明示stopまでFOC継続しSPI/センサー/timeoutは0だった。

従来のtransfer_maxは応答デコード前の時刻までしか測らず、その後のプリエンプトや角度公開を
含まない。今回、transfer_max=95.66 µsでも実際の公開には120.78 µsかかることが分かった。

結論：通信クロックが律速ではなく、高優先度ISRによるDMA処理の遅延・中断が長時間化の主因。
高優先度ISR自身の実行時間も原因の一部なので、次はその削減と処理配置を検討する。
タイムアウト判定がハード転送と応答処理を同じ状態で扱う点も整理が必要だが、
判定を除くだけでは角度鮮度問題が残る。今回は計測のみで、優先度・保護閾値は変更していない。

Release/Debugともビルド成功。実機には計測対応Releaseを残し、PWM停止・COM11解放済み。

## ADC起点直列化・頂点PWM反映版

FOC時の処理をADC完了へ移動：電流取得/保護→FOC計算→CCR preload書込み→SPI DMA開始。
TIM1はmain/ADC周期/nFAULTの独立監視のみ。校正・六ステップの周期処理は従来の経路。
開始時は全出力OFFで中央揃えのDIRを設定し、UG後CNT=ARRから下降する。RCR=1なので次の頂点で更新。
CH4のPWM1立上りはARR-1を下降時に通過する位置であり、ADC完了は頂点後になる。
実測もTIM更新/ADC開始のCNTがARR未満、DIR=1で、頂点後の下降区間だった。
波形のオシロスコープ測定はしていない。

直列化のみのDebugは角度鮮度停止が残ったため、as5047p/current_sense/motor_controlにも-O2を適用。
既存のFOC/電圧生成/CMSIS三角関数と合わせて周期処理の実行時間を優先した。
状態表示は1ループ1行に分割し、表示中のmain stale停止を解消した。
取消済みのADC内部区分計測は撤去。IRQ全体のトレースは維持する。
