# 循環DMAとFOCの位相設計・評価

## 最新の具体案

[FOC開始時にTIM1の位相をTIM8へ合わせる設計](encoder_phase_start_plan_2026-10-07.md)を第一候補とする。
50 µs化後は同一クロック・同一周期のため、TIM8を止めずFOC開始位置だけを合わせる案を先に評価できる。
これなら毎周期Resetに伴う通信切替・時刻基準の作り直しを避けられる。
CubeMXの追加変更は不要。以下のTRGO→Reset案は、この方法が成立しない場合の代替案として残す。
具体案を実装し、正逆運転と再始動を検証済み。
[検証記録](encoder_phase_validation_2026-10-08.md)に測定結果・未解決の起動時エラーを記載する。

## 方針更新：TIM1を意図どおり50 µsへ揃える

ユーザーの意図はTIM1も50 µsだったため、以下の初期案の「TIM8を49.9875 µsへ合わせる」より、
TIM1を50 µsに修正する方針を優先する。下記本文の旧設定値・計算は調査時点の記録として残す。

CubeMXでまず変更するのはTIM1の次の2点:

- Counter Period (ARR): 3999 → **4000**。
- PWM CH4 Pulse (CCR4): 3998 → **3999**。ADCの起動位置をARR-1に維持する。

TIM1のPSC=0、Center Aligned 1、RCR=1を維持する。
TIM8 ARR=7999、TRGO/Slave設定はこの段階では変更しない。
160 MHz基準で中央揃えの周期は `2*ARR*(PSC+1)/f_TIM`、4000なら50 µs。
上向きTIM8は `(ARR+1)*(PSC+1)/f_TIM` なので7999で50 µsになる。
[ST公式のカウント方式の説明](https://wiki.st.com/stm32mcu/wiki/Getting_started_with_TIM)

2026-10-07、ユーザーによる再生成を確認した。main.c/.iocの変更はTIM1 ARR=4000、CCR4=3999。
生成部分はこちらでは編集していない。
FW側のMotorControl_GetControlTickHzには中央揃えにARR+1を使う不整合があったためARRへ修正した。
中点、手動オフセット、六ステップ、電圧ベクトルのPWM比較値換算もARR基準へ揃えた。
CurrentSenseのログ周期計算は既にARR基準のため変更なし。

Release/Debugビルド成功。両ELFで既存H2/PI試験とtools/test_motor_period.pyが成功した。
後者はARMエミュレーションで周期50 µs、ゼロ電圧のCCR=2000、
24 V・角度0・vd=1 V/vq=0でCCR=(2125,1875,1875)、ARR=0の初期化拒否を確認する。
クロック取得と停止処理はスタブであり、実際のPWM波形の試験ではない。
この50 µs版の実機評価も完了した（以下）。

### 再生成後の評価順序

まず追加の同期機構を入れず、50 µs版で無負荷±0.3 V、ADCログ100 Hz・各30秒を再測定する。
角度ageの中央値/p99、FOC age_max、受信公開遅延、エラーを既存A/Bと比較する。
起動し直した複数回でも測定し、固定された開始位相の当たり外れを調べる。
同周期化は周波数差を除くが、不利な位相を固定する可能性もあるため、改善はまだ断定しない。
詳細8点のトレースは追加負荷があるため、A/B比較では同じ計測構成へ合わせる。

その後も公開がADCに遮られる場合にTIM1→TIM8同期を検討する。
今後の同期候補ではTIM1 ARR=4000/CCR4=3999、TIM8 ARR=7999を維持する。
下記初期案のTIM8 ARR=7997は採用しない。CCR1=5280/CCR2=5440は未検証の位相候補。
TRGO/Slave設定の追加変更は、開始・停止時の通信切替と時刻基準の設計後に依頼する。

## 今回の判断

まず1フレーム/制御周期を維持し、TIM1にTIM8を同期させる小規模な比較を推奨する。
目的は相対位相の移動と受信公開待ちを減らすこと。要求から応答まで1周期待つ構造は残るため、
旧方式のADC時点中央値23 µsに戻せるとは見込まない。
同期で効果が不足する場合にだけ、1周期内の要求/応答2フレーム化を検討する。
sin/cos共有、割り込み優先度変更、モーターPWM周波数変更は混ぜない。

この文書は設定・実装案であり、現行FWと組み合わせてCubeMX設定だけを変更してはいけない。
以下は周期修正前の初期案の記録であり、現在の実装状況は冒頭を参照する。

## 現状の時系列と周期差

コードの設定値:

- TIM1: timer clock 160 MHz、PSC=0、center aligned、ARR=3999、RCR=1。
  完全な上下カウントは7998 tick = 49.9875 µs。FOC時の更新基準は頂点。
- ADC injected: TIM1_CC4 rising、CCR4=3998。頂点直後の下降側で起動。
  IRQ到着時刻は変換時間と割り込み待ちを含む。
- TIM8: 同じ160 MHz、PSC=0、up、ARR=7999。
  8000 tick = 50 µs。CNT=6400でCS Low、6560で送信DMA要求。
- SPI: 5 MHz/16 bitなので線上の16 clockは3.2 µs。DMAバス待ち等は別。
- 受信は前フレームの要求に対応する。受信処理の優先度はTIM1/ADCより低い。

両タイマーは同じクロックでも分周比が違う。毎制御周期に2 tick = 12.5 nsずれ、
約4000周期（約0.2秒）で相対位相が一周する計算になる。
ソフトウェアで一度開始位相を揃えるだけでは解消しない。
7998 tick周期は保存済みトレースの約49.9875 µsとも整合する。

従来の40/41 µsはTIM8自身の開始からの値で、ADC頂点から40/41 µsという意味ではない。
実測のADC ISR約29〜30 µs、TIM1約3.5 µsに受信処理が重なると公開が遅くなる。

## 同期経路

ST公式RM0440 Rev 9 Table 267（p.1148）はTIM8 ITR0=TIM1_TRGOを示す。
同29.3.30（p.1227）はスレーブReset modeによるカウンター/プリスケーラー再初期化を説明する。
[ST公式RM0440](https://www.st.com/resource/en/reference_manual/dm00355726.pdf)

候補はTIM1 TRGO=Update → TIM8 ITR0 → Slave Reset mode。
TIM1のTRGO2は使わず、ADCの既存TIM1_CC4入力も維持する。
Reset modeの再同期遅延とUEV/preloadへの作用は実機で検証する。

## 第一段階の設定候補

| 項目 | 現状 | 候補 |
|---|---|---|
| TIM1 TRGO | Reset | Update event |
| TIM1 ARR/PSC/RCR/CH4 | 3999/0/1/3998 | 維持 |
| TIM8 Slave mode | 無効 | Reset mode |
| TIM8 Trigger source | 未使用 | ITR0（TIM1_TRGO） |
| TIM8 ARR/PSC | 7999/0 | 7997/0（7998 tick周期） |
| TIM8 CH1 PWM1 CCR | 6400 | 仮5280（33 µsでCS Low） |
| TIM8 CH2 compare | 6560 | 仮5440（34 µsで送信） |
| SPI、DMAモード、IRQ優先度 | 現状 | 維持 |

CCR値は開始候補であり確定値ではない。ADC IRQ終了〜次のADCの空き時間で、
SPI終了と受信公開を完了できる位相をトレースで選ぶ。
計測フックなし/通常トレース時を基準とし、内部8点計測版の追加負荷を混ぜない。

FOC頂点を0、P=49.9875 µsとした概算:

```text
0                 約33       34       37.2       約46        P
| TIM1/ADC処理 ------|        |SPI 3.2us| RX処理 ----|         |次のADC
                    CS Low   TX                             CS High/同期
```

ADC/TIM1終了時刻、DMA待ち、トリガ伝搬を含めて公開が次のADCより早いことが成立条件。
上記は測定済み各処理時間からの概算で、保証値ではない。
Pの直前に公開される角度は「前周期の34 µsの要求」への応答なので、
次のADC入口での要求経過時間は概ね `2P - 34 µs + ADC入口までの時間`。
約66 µs＋ADC入口分であり、現状中央値87〜89 µsからの改善候補にはなるが、
50 µsのパイプライン待ちを消すものではない。診断挿入時の最大値は別途評価する。

## 設定だけを先行変更できない理由

1. 現行ドライバーは8000 tick周期を固定検証・加算している。
   7998 tickへの変更、要求時刻の基準、締切検査を一貫して更新する必要がある。
2. TIM1起動/再始動のMotorControl_ResetTimerPhaseはUGを発行する。
   TRGO=UpdateではTIM8へ意図しないリセットが伝わり、SPI途中のCSを切る恐れがある。
   起動準備中は通信を停止してCS High、初期化後に同期を有効化し、最初の応答を捨てて診断から再開する。
3. TIM1停止中も角度取得が必要。停止時は安全なCS High区間で同期を外し、同周期の自由走行へ戻す。
   ADC単独、校正、六ステップはTIM1の更新位相がFOCと異なるため、同期対象をFOCに限定する案。
4. 動作中のTIM1消失を単なる自由走行で隠さない。既存FOC watchdogに加え同期状態の整合性を検証する。
5. DWTの要求時刻を遅れた受信IRQから都合よく更新してはいけない。
   同期後のハードウェア位相に基づく基準確立と再同期時のサンプル無効化が必要。
6. 現在のガードは次の送信までの期限で、ADCが使う時刻までの期限ではない。
   通信に間に合っただけで同期の目標達成とせず、公開完了→ADCの余裕を別計測する。

これらをUSER CODE/専用ドライバー側で具体化してから、上表をCubeMX設定依頼として確定する。
生成部分はこちらでは編集しない。

## 第二段階：要求/応答を1周期内へまとめる案

さらに旧方式に近い鮮度が必要なら、短い間隔の2フレームをハードウェアで発生させる。
単純な40 kHz化では受信IRQも増え、診断要求の扱いとDMAバッファ構成も変わる。
2語ごとのTCで処理する案ならIRQ回数を抑えられるが、CH1 PWMだけで任意の2パルスを作ることはできず、
比較値更新DMAや別のタイマー構成を含めた設計になる。既存処理へ大きく手を加えない方針から今回は保留。
同期のみで効果が不足なら、旧方式を継続採用する判断も残す。

## 検証と採用条件

- まずPWM停止で同期切替・初回応答破棄・診断・watchdogのソフトウェア試験。
- 実機は無負荷±0.3 V、従来と同じログなしトレース＋ADCログ100 Hz正逆各30秒。
- 0.2秒より十分長く観測し、公開位相が流れず、次のADC前に公開されることを確認。
- ADC時点の角度age中央値/p99と全周期のFOC age_maxを別々に比較する。
- TIM1/ADC/RX占有時間、ログ欠落、PARERR、欠落フレーム、再始動を評価。
- 同期切替や診断時に250 µsの角度制限を緩めない。遅延を見かけ上減らす時刻付替えもしない。
- 旧方式に対し鮮度・CPU負荷・複雑さの釣合いが改善しないなら採用しない。

オシロ/ロジアナがある場合はCS/SCKとADCまたはTIM1位相マーカーを同時観測する。
通常のトレースだけでは実際のSPI開始・CS途中切断まで証明できない。
位相マーカーを端子へ出すには基板の空き端子確認と別途設定が必要。現時点では端子を指定しない。
